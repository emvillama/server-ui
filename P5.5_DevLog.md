# Phase 5.5 DevLog: Persona Feature Resources (Favorites & Pantry)

## Context

Phase 6 (frontend) started from the assumption that a persona is just a tab
with different chat context injected -- different skills, knowledge, tools.
That held up until designing the Recipe Recommender's tab layout (Favorites,
Pantry, Chat, Options) made it clear some personas need actual persistent,
queryable resources of their own, not just different chat behavior. Favorites
and Pantry aren't things the model produces per-message; they're things a
user builds up over time and expects to still be there next session.

This phase pauses Phase 6 frontend work to build that backend support first,
per the project's decision-first discipline -- building UI against endpoints
that don't exist yet isn't a real Phase 6 start, it's guessing.

## Components (build order)

**1. `Favorite` and `PantryItem` models**
Both follow the exact FK/cascade shape `Knowledge` already established:
`persona_id` FK with `ondelete="CASCADE"`, `passive_deletes=True` on the
relationship so SQLite's own cascade handles cleanup on persona deletion
rather than the ORM nulling out the FK first. `Favorite` stores `title`,
`ingredients` (JSON list[str]), `steps` (JSON list[str]) -- normalized
columns rather than a single JSON blob, since the recipe shape is fixed and
known, and Pydantic gets to validate it. `PantryItem` adds a composite
`UniqueConstraint` on `(persona_id, name)` so the upsert-merge logic in the
service layer can't be raced past by two concurrent adds.

**2. Pydantic schemas**
`FavoriteCreate`/`FavoriteOut`, `PantryItemCreate`/`PantryItemUpdate`/
`PantryItemOut` -- same separation-from-the-DB-model reasoning as every
other schema in this codebase. `PantryItemCreate` and `PantryItemUpdate`
are deliberately different shapes even though they cover mostly the same
fields: `Create` feeds the upsert-add endpoint (quantity/unit describe
what's being *added*), `Update` feeds direct edits (every field optional,
omitted-vs-null semantics matching `PersonaUpdate`).

**3. Service layer**
`favorite_service.py` is intentionally thin -- favorites are just
structured data handed over already-shaped, not something this layer
computes. `pantry_service.py` carries the one genuinely non-trivial piece
of logic in this phase: `upsert_pantry_item()`'s merge rules. Same name +
same unit (including both `None`) sums the quantities; anything else
(mismatched unit, or either quantity missing) overwrites rather than
attempting unit conversion. Matching is exact-string, case-sensitive --
"Eggs" and "eggs" are different pantry rows. Both are simplifications
worth revisiting if they turn out to matter in practice, but real unit
math and fuzzy name matching were out of scope for a personal-scale tool.

**4. Routers**
`/personas/{persona_id}/favorites` and `/personas/{persona_id}/pantry`,
nested the same way `/knowledge` is -- these resources don't exist
independent of a persona. Pantry's `POST` follows real REST status-code
conventions: `201` when `upsert_pantry_item` created a new row, `200` when
it merged into an existing one, decided by setting `response.status_code`
explicitly rather than a fixed decorator value.

**5. `return_recipe` tool + terminal shortcut**
Registered in `tool_registry.py` alongside `dice_roller`, but behaves
differently on purpose. `dice_roller` is a "fetch a value, keep talking"
tool -- the model gets a result and makes a follow-up call to write prose
around it. `return_recipe` is terminal: its arguments *are* the final
answer, not something to hand back to the model for prose-ification. If
`run_chat()` sent it through the normal round trip, the structured
`{title, ingredients, steps}` would get consumed by the model and never
reach the frontend. Instead, `run_chat()` checks for `return_recipe`
specifically among `tool_calls` and short-circuits: no follow-up `chat()`
call, arguments returned directly as `structured_output`. `ChatResponse`
gained that field (`dict | None`, `None` for every ordinary response
including non-terminal tool use) to carry it out through `/chat`.

**6. `capabilities.features`**
New field on the `Capabilities` schema, same shape as `tools`/`skills` --
a list of sub-resource tab names (e.g. `["chat", "favorites", "pantry",
"options"]`). Unlike `tools`/`skills`/`knowledge`, this has no backend
enforcement -- the Favorites/Pantry endpoints work regardless of what a
persona's `features` list says, since a `persona_id` is a `persona_id`.
It exists purely so `GET /personas` can tell the frontend which tabs to
render, extending the tab-routing plan from Phase 6's `ui_theme` field
down to the sub-tab level.

**7. Tests**
`test_favorites.py` and `test_pantry.py` at the endpoint level (sync,
`TestClient`, no `pytest` import needed -- same shape as
`test_personas.py`), plus `test_run_chat_recipe.py` for the terminal
shortcut specifically: short-circuit behavior, exact argument pass-through,
ignoring other tool calls in the same response, and a missing-title
fallback. `test_run_chat_tools.py` got the 2-tuple-to-3-tuple unpacking
updated across its four assertions that actually unpack the return value.

## Bugs Found and Fixed

Several of these only surfaced during empirical confirmation against real
pytest/SQLite -- exactly the value of not marking a phase done on code
review alone.

- **Knowledge-flag regression.** An early full-file rewrite of
  `persona_service.py` reconstructed `run_chat()`'s knowledge-retrieval
  block from an existence-only check, dropping the `capabilities.knowledge`
  gate that Phase 5 had already shipped. Caught by
  `test_run_chat_skips_retrieval_when_flag_off_even_with_knowledge_rows`
  failing -- fixed by wrapping the existence check inside a
  `knowledge_enabled` check on `capabilities.get("knowledge", False)`.

- **`return_recipe`'s reply was a raw dict, not a string.** The terminal
  shortcut originally returned the tool's `arguments` dict as both
  `structured_output` *and* `reply`, but `ChatResponse.reply` is typed
  `str`. Fixed to return a short fallback string (`"Here's your recipe:
  {title}"`, defaulting to `"Recipe"` if `title` is missing) while
  `structured_output` still carries the full dict.

- **Duplicate `add_pantry_item` route.** A REST-conventions fix (200 vs
  201 based on create-vs-merge) was communicated as a standalone snippet
  rather than a full file, and the original version never got removed --
  leaving two `@router.post("")` functions with the same name in
  `routers/pantry.py`. FastAPI silently registered the first one, which
  called the *old* `upsert_pantry_item` signature and tried to validate
  its `(item, created)` tuple return against `PantryItemOut`, failing
  every POST-dependent pantry test with `ResponseValidationError`. Fixed
  by removing the stale duplicate.

- **`models/favorite.py` saved as `favorites.py`.** Plural filename vs.
  the singular convention every other model file uses
  (`persona.py`/`knowledge.py`), breaking `from
  backend.models.favorite import Favorite` in the service layer.
  Renamed to match the existing convention.

- **Stale Phase-4-era test.**
  `test_run_chat_skills_come_before_knowledge_block` predates Phase 5's
  `capabilities.knowledge` gate and asserted retrieval on row-existence
  alone. Fixed by adding `knowledge=True` to that test's persona
  capabilities -- the two test files (`test_run_chat_skills.py` and
  `test_run_chat_knowledge.py`) were asserting contradictory things about
  the same code path until this was reconciled.

## Empirical Confirmation

Full automated suite: 172/172 passing. Live walkthrough against the real
backend, real SQLite file, and real Ollama on the RX 580: persona creation
with the Recipe Recommender's actual capabilities, a live `/chat` call that
triggered a real `return_recipe` tool call from `llama3.1:8b`, saving that
result as a Favorite, and the full Pantry upsert path -- same-unit merge,
cross-unit overwrite -- all confirmed working as designed, not just as
tested.

## Not Built Yet

- **CORS middleware.** Still not added to `main.py`. Everything in this
  phase is confirmed working over direct API calls, but the frontend can't
  reach any of it -- including the pre-existing endpoints from earlier
  phases -- until this is in place. Next concrete step before frontend
  work starts.
- **Coding Assistant's Debugging/File Generation tabs.** Deliberately not
  designed alongside Favorites/Pantry -- those need their own
  explicit-decision pass (what does "backend support" even mean for a
  debugging tab?) rather than being shoehorned into this phase's shape.
- **Unit conversion in Pantry.** Mismatched-unit adds overwrite rather
  than convert (e.g. "2 cups" + "500 g" doesn't attempt to reconcile).
  Simple by design for now; revisit if it turns out to matter in practice.
- **Pantry item rename.** `PantryItemUpdate` has no `name` field --
  renaming reads as delete-and-recreate, since `name` is also the upsert
  key. Small addition if wanted, but changes the service's conflict
  handling.
- **Seed data for the Recipe Recommender persona.** The persona created
  during empirical confirmation was a one-off manual `curl` call, not
  something the app creates automatically -- worth deciding whether
  personas like this get seeded on startup or stay a manual setup step.
